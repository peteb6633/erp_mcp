## What was asked

Pete asked for "an alternate package to replace Frappe Assistant Core". That app connects AI clients to ERPNext over MCP, but it is AGPL-3.0 and ships tools that run arbitrary Python and SQL. Node4 wants to offer ERPNext to SMB clients, customised per client with AI tools, so it needs a connector it can host without AGPL duties and without those tools.

Pete set three things: the licence, the write scope and where the code goes. Almost everything else below was decided by the model.

## Security and risk

Two review rounds by a separate agent that checked each claim against the Frappe v16 source. All findings below were fixed and the attack inputs re-run on a live site.

Round one:
- **Hidden save keys.** Keys such as `_action` or `flags` in `values` could change how Frappe saves a document, for example rewriting a submitted invoice without touching its ledger entries. Fix: only real fields of the DocType or its child tables are accepted.
- **Foreign child rows.** An update could name a child row belonging to another document. Fix: a row `name` must be one of this document's own rows; named rows are merged over their current values.
- **Link traversal in filters.** Filters such as `allocated_to.api_key` or 4-part filters naming another DocType could probe blocked tables through joins. Fix: filters may name only the DocType's own fields and its child tables.
- **Child tables of blocked DocTypes** (for example User Social Login under User) were reachable. Fix: a child table is blocked if any parent is.
- **Case variants.** `user` found `User` and slipped past the block list (found in testing, before review). Fix: resolve the exact name first, then check.
- **Custom SQL reports.** A caller with rights to create a Query Report could read `tabOAuth Bearer Token`, including via a Custom Report wrapping it. Fix: Report is read-only through MCP, custom SQL and script reports are off by default, and Custom Reports are judged by the report they wrap.
- **Browser session fallback.** A logged-in browser plus a junk bearer token reached the tools, because a failed header check fell back to the cookie. Fix: refuse any request whose session did not come from the header (see Traps).
- **Rollback.** Savepoint rollback did not cover everything a tool could do. Fix: full rollback on failure, before the audit row and error log are written.
- **Search fields** could include fields above the user's permission level. Fix: only permitted fields are searched.

Round two:
- More DocTypes made read-only: User, Custom Role, Workflow, website scripts and settings, web templates, letter heads.
- Child tables can no longer be written directly, only through their parent.
- A non-string row `name` is refused.
- Documents returned after create, update, submit and cancel now hide fields above the user's permission level.
- The OAuth client allow-list matches client IDs only, not names.

Accepted, not fixed:
- Code in ERPNext or other apps that commits the transaction itself defeats the rollback.
- Anything the connected user's roles already allow is allowed. Connect with a dedicated user with only the roles the job needs.

## Traps for maintainers

These look odd. They are deliberate. Do not "fix" them without a new note. Each one is pinned by a test in `tests/test_traps.py` and marked with a comment in the code.

- **`frappe.session.sid != frappe.session.user`** in `erp_mcp/api.py` (`mcp`). When Frappe authenticates from the `Authorization` header it sets the session ID to the user's name; a browser session keeps a random ID. This is how the endpoint tells header auth from a cookie. It looks like a typo. It is the security check that closed the session-fallback hole.
- **Order in `_invoke`'s `finally`** in `erp_mcp/api.py`: roll back first, then write the Error Log, then the audit row. Logging before the rollback loses the log.
- **The traceback is captured in the `except` block and logged later** in `erp_mcp/api.py` (`_invoke`). The `except` block re-raises as a `ToolError`, so by the `finally` block the original traceback has been replaced.
- **401 header built with `frappe.integrations.oauth2.get_resource_url()`** in `erp_mcp/api.py` (`_unauthorised`), not the request host, so it matches what Frappe's discovery documents advertise.
- **Request cache via `getattr(frappe.local, "erp_mcp_parents", None)`** in `erp_mcp/guard.py`. The first version used `frappe.local.__dict__.setdefault(...)`, which failed on the live test site. `frappe.local` is a context-local proxy, not a plain object.
- **`allowed_oauth_clients` matches IDs only** in `erp_mcp/guard.py` (`allowed_client`). Matching names looks friendlier and is unsafe.
- **`frappe.get_list(..., limit=, offset=)`** in `erp_mcp/tools/builtin.py`. The old names `limit_page_length` and `limit_start` are deprecated in v16 and go in v17. Do not switch back. (The build session recorded that the old names misbehaved; current v16 source does not bear that out. See [2026-10-01-whoami-limit.md](2026-10-01-whoami-limit.md).)
- **`describe_doctype` hides read-only fields by default** in `erp_mcp/tools/builtin.py`. This is to save context, not a bug; `include_read_only` brings them back.
- **`except (A, B):` with brackets**, and ruff's `target-version = "py311"` in `pyproject.toml`. Ruff targeting Python 3.14 rewrote these to the bracket-free form, which is a syntax error before 3.14.

## How it was checked

- Local bench: Frappe 16.35.1, ERPNext 16.36.1, MariaDB, Python 3.14.3.
- The sign-in flow a Claude connector uses, simulated end to end: 401 discovery, dynamic registration, user sign-in and consent, PKCE code exchange with a `resource` parameter, a bearer call and a token refresh.
- Create, update, submit and cancel a Sales Invoice; run Accounts Receivable and General Ledger.
- Every review finding re-run as an attack and shown to fail with a clear message. A failed create leaves no rows.
- Unit tests for the framework-free protocol layer (`tests/test_protocol.py`) and a read-only smoke test (`scripts/smoke_test.py`).
- **Not tested:** with Claude itself; behind Frappe Cloud's proxy (the smoke test warns if the site reports an `http://` resource URL while served over `https://`).
